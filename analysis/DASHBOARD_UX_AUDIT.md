## 2. Prioritized findings

### P0

#### UX-01 — "Check verification" always reports failure, while a real verification endpoint exists and is never called [P0, VERIFIED]
- **Problem:** The audit trail's "Check verification" button never verifies anything. It refreshes the live data and then unconditionally reports failure.
- **Evidence:** `src/views/AuditTrailView.tsx:97-115` — `handleVerifyIntegrity` calls `refreshLive()` then sets the notice `"Not verified — no cryptographic verification available. The control plane does not expose an audit-chain verification result, so the hashes shown are record digests as returned by the server and have not been independently re-verified here."` The file header (`:6-10`) asserts the same, and the per-record modal repeats it (`:421-424`: `"Not verified — no cryptographic verification available for this record."`). The backend **does** expose it: `GET /api/audit/verify` (`src/ai_bridge/control/routers/audit.py:73-76`, `return dbmod.verify_audit_chain(conn)`). Grep for `verify` in `apps/dashboard/src/api.ts` returns zero hits; no dashboard file calls it.
- **User impact:** The audit trail is the evidentiary core of a control plane. An operator who needs to prove chain integrity — the exact reason the view exists — is told verification is impossible, and may export or quote the "not verified" notice. The honesty banner introduced to fix fabrication (D-02) is now itself inaccurate.
- **Recommendation:** Add `verifyAudit()` to `api.ts` (`GET /api/audit/verify`), call it from "Check verification", and render the real result (valid/invalid, blocks checked, first bad block if any). Until then, reword the notice to "verification not yet wired into this view" rather than "the control plane does not expose" it. Also add retention UI (`POST /api/audit/retention`, `audit.py:78-95`) — there is currently no dashboard path to prune the ledger.

### P1

#### UX-02 — `#/live` has no sidebar, no command palette, no TopHeader: the landing page strands the user [P1, VERIFIED]
- **Problem:** The post-login landing page is a navigation dead end. It renders outside the app shell, so it has no sidebar, no command palette, and no TopHeader (including the emergency-stop button).
- **Evidence:** `src/App.tsx:189` — `if (currentView === "live") return <LiveControlView />`, bypassing `AppShell` entirely. `src/views/LiveControlView.tsx:256-268` renders its own minimal topbar (Brand + Language/Density/Refresh/Sign out only). The command palette is mounted inside `AppShell` (`src/shell/AppShell.tsx:167`), so Ctrl/⌘K does not exist on `#/live`. The only link from `#/live` to any demo view is the empty-state secondary button `"Explore demo overview"` (`LiveControlView.tsx:285-295`), shown only when the control plane is unreachable/unsigned-in. Post-login landing is `#/live` (`src/views/LoginView.tsx:62-64`).
- **User impact:** Every signed-in user starts on a page from which there is no visible path to Devices, Tasks, Desktop, Policies, Audit, or any other view. To reach them the user must know to type a hash or use the 9 LiveWorkspace sections — which are themselves a parallel, simplified duplicate of those views (see UX-16).
- **Recommendation:** Render the standard `AppShell` (sidebar + palette + TopHeader) around `#/live`, or add an explicit nav (sidebar or link row) to `LiveControlView`. This is the single worst navigation defect found.

#### UX-03 — Eight destructive actions fire on a single click with no confirmation and no undo [P1, VERIFIED]
- **Problem:** Irreversible actions execute immediately, with no confirm step and no undo anywhere in the app.
- **Evidence:** Delete device — `src/views/DevicesView.tsx:261-275` `handleDeleteDevice` → `api.deleteDevice` immediately; button `:617-631` is a plain `JXButton color="error"` with `onClick={() => handleDeleteDevice(device)}`. Revoke device credentials — `:242-256` → `api.revoke` immediately; button `:595-610`. Delete task — `src/views/TaskQueueVisionView.tsx:309-321` → `api.deleteTask` immediately. Clear tasks (bulk delete of all matching tasks) — `:327-340` → `api.clearTasks` immediately. Delete approval — `src/views/HumanApprovalsView.tsx:259-268` → `api.deleteApproval` immediately. Delete workflow — `src/views/WorkflowsView.tsx:246-256` → `api.deleteWorkflow` immediately; button `:462` is a raw red button. Delete workflow template — `:272`. Revoke OAuth client — `src/views/ConnectionsView.tsx:483-495` → `api.deleteOAuthClient` immediately. Daemon start/stop/restart — `src/views/Device360View.tsx:476-491` dispatches `systemctl`/`sc` commands immediately (a `stop` on a production service is one click). Grep for `undo` returns only the word "undone" in a confirm string (`src/views/SecurityPoliciesView.tsx:284`); there is no undo anywhere.
- **User impact:** One misclick permanently deletes a device record, revokes credentials, or wipes a filtered task set. The same destructive class *is* guarded elsewhere (delete agent/policy version get `window.confirm`; kill process gets a modal; reboot gets hold-to-confirm), so an operator who learns "deletes ask first" from the policy screen will be surprised on the devices screen.
- **Recommendation:** Route all irreversible actions through one `ConfirmDestructive` (GlassModal) showing the object name and consequence; reserve `window.confirm` for nothing (unstyled, unbranded, blocks the tab); keep hold-to-confirm only for emergency stop, where speed matters. The kill-process modal (`Device360View.tsx:1404-1440`, explicit PID/name/user, protected-process guard, Cancel + Kill) is the template. Also label what Revoke vs Delete does ("Revoke: invalidates the device's credentials; the device can re-enroll" vs "Delete: removes the device record").

#### UX-04 — Tier 3/4 task dispatch needs no confirmation, including via Ctrl+Enter [P1, VERIFIED]
- **Problem:** Elevated shell and kernel commands dispatch on a single click, with no last-chance check.
- **Evidence:** `src/views/TaskQueueVisionView.tsx:256-285` — `handleDispatch` validates only that the JSON parses (`:262-266`) and then dispatches immediately; the global shortcut `:579-588` binds Ctrl/Cmd+Enter to `handleDispatch()` with `preventDefault()`. Tool options are labelled with tiers (`:725-732`, e.g. `"run_shell [Tier 3: Elevated Shell]"`), and the risk tier is auto-derived (`:191-221`, `tier4_kernel` for kernel tools), but there is no confirm step, no re-typing, no hold-to-confirm for Tier 3/4. The quick-dispatch modal in `src/views/DevicesView.tsx:900-929` offers `run_shell` with the note `"(shell — requires approval / tier)"` (`:910`) and a single "Execute Tool" button (`:928`) — no tier shown, no confirm.
- **User impact:** A slip (wrong device selected, wrong tool, stray Ctrl+Enter while editing JSON) can run an elevated shell command on a fleet device. The approval gate is server-side and invisible; the UI gives no last-chance check.
- **Recommendation:** Require an explicit confirm (modal or hold-to-confirm) for Tier 3/4 dispatch, showing device, tool, tier, and a truncated args preview; make Ctrl+Enter require the same confirm. Related: "Unrestricted" policy (which removes ALL limits) gets only a native `window.confirm` (`src/views/SecurityPoliciesView.tsx:216`) — use hold-to-confirm + typed acknowledgement, matching emergency-stop treatment.

#### UX-05 — The same semantic state is styled differently on different screens [P1, VERIFIED]
- **Problem:** There is no shared status-badge component, so the same state has different colours, sizes, and shapes depending on the screen — in a safety-critical control plane where colour is the fastest signal.
- **Evidence:** Task "completed": `src/views/TaskQueueVisionView.tsx:639-646` `getStatusBadge` — `bg-emerald-500/15 text-emerald-300 border border-emerald-500/30`, icon `CheckCircle2`, `text-[11px]`; vs `src/views/WorkflowsView.tsx:47-55` `statusClass()` — `bg-emerald-500/20 text-emerald-300 border border-emerald-500/40`, no icon, `text-[10px] uppercase`. Task "running": cyan (`bg-cyan-500/15 text-cyan-300`, spinning `RefreshCw`) in TaskQueueVision (`:648-653`) vs indigo (`bg-indigo-500/20 text-indigo-300`, no icon) in Workflows (`:48`). Live panels render the same statuses as plain text with no badge and no colour except failure (`src/views/live/shared.tsx:35-38` `taskStatus()`; `src/views/live/TasksPanel.tsx:104`). Success is emerald in `ProductNotice` (`src/ui.tsx:211-227`) but indigo in `src/views/WorkflowsView.tsx:361` ("ok" kind renders `bg-indigo-950/70 border-indigo-500/40 text-indigo-300`). Device online: `ProductStatusDot` emerald `#34d399` (`src/views/DevicesView.tsx:493-508`) vs the `.product-status` CSS token `#6ee7b7` (`src/tailwind.css`). `JXBadge` (`src/ui.tsx:312-316`) is explicitly "label wrapper only — no status→tone logic".
- **User impact:** An operator scanning two screens cannot learn one code for running/completed/failed/success/error.
- **Recommendation:** Add a `StatusBadge`/`Tone` map in `ui.tsx` (status → {bg, border, text, icon, label}) covering task/device/workflow/approval/log states, and migrate the four sites to it; delete `getStatusBadge` and `statusClass`.

#### UX-06 — Signed-in demo views show seed data with no sync/loading indicator, and there is no toast system [P1, VERIFIED]
- **Problem (a):** The store initialises with 40 fake devices and other fixtures before any auth (`src/state/dashboardStore.ts:722-755`), and `syncWithBackend()` runs 50 ms after mount plus every 15 s (`:764-772`) with **no loading flag** — grep for `syncing|isSyncing|loading` in `dashboardStore.ts` finds only the scheduling. Views read the store directly (e.g. `src/views/DevicesView.tsx:68-74`), so on sign-in the user sees the fake fleet, silently replaced by live data when the fetch lands. There is no "syncing" indicator, no skeleton, and no staleness marker on demo views. The `Freshness` component exists (`src/components/Freshness.tsx:5-45`, with loading/stale/relative-time states) but is used only in `LiveControlView.tsx:268` and `OverviewView.tsx:15`. A failed sync leaves seed data on screen with no warning. The store's `gatewayStatus: "degraded"` is set in the sync catch (`dashboardStore.ts:1075`) but never read anywhere outside the store. `OverviewView.tsx` has zero error handling (grep for `error|Error` returns zero matches). SSE failures are swallowed silently (`dashboardStore.ts:786-808` — `catch { // Fallback to interval polling }`, retry after 5 s, no notice).
- **Problem (b):** There is no toast/notification system (grep for `toast|Toast` returns 0 hits). Feedback is inline, per-view, via four parallel mechanisms: `ProductNotice` (`src/ui.tsx:211-227`, `role="status"`), `JXAlert` (library, severity + title + description), ad-hoc inline notice `div`s (`src/views/WorkflowsView.tsx:360-364`), and plain `<p>` feedback (`src/views/Device360View.tsx` `actionFeedback`). Auto-dismiss timers are inconsistent and asymmetric: 1,200 ms (`DevicesView.tsx:293` dispatch success — which also closes the modal after 1.2 s, so the user may not finish reading it), 3,000 ms, 3,500 ms, 4,000 ms, 2,000 ms for "Copied" states. Success auto-clears after 3 s but failure persists until the next action (`DevicesView.tsx:242-256` revoke, `:261-275` delete); `WorkflowsView.tsx:360-364` notices never auto-dismiss (manual X only). An error rendered in a success-styled alert exists: `src/views/DevicesView.tsx:910-912` renders `dispatchSuccessMsg` (which holds `"Dispatch error: …"` on failure, `:297`) inside `<JXAlert severity="success" …/>` — users learn that green can mean failure.
- **User impact:** The user cannot tell whether the fleet list they are looking at is live data or the seed, or whether a sync is in flight; a success message can vanish before it is read (1.2 s), a stale failure notice can be mistaken for current state, and feedback is positional (the user must be looking at the right panel).
- **Recommendation:** Add a `syncState: "loading"|"live"|"error"|"stale"` to the store, surface it via `Freshness` in every demo-view header, show an explicit error banner with Retry when sync fails, and expose stream state (connected / reconnecting / polling-fallback). Introduce one `useNotice` + `NoticeStack` (or adopt JXUI `JXSnackbar`/`ProgressToast`, named in the design spec §1A.4) with one policy (success auto-dismiss 5 s, error persists until dismissed, both with a dismiss button and `role="status"`/`role="alert"`). Never render error text in a success alert.

#### UX-07 — The enrol modal's three controls silently discard what the user enters [P1, VERIFIED]
- **Problem:** The main enrolment form invites the user to make choices that are never sent to the API.
- **Evidence:** `src/views/DevicesView.tsx:724-760` — "Target Architecture & Role" select labelled `"(display only — not sent to enroll)"` and an option `"Confidential Compute (SGX / SEV) — decorative, not wired"` (`:739-741`); "Sandbox Home Directory" labelled `"(not wired to enroll API)"` (`:744-755`); "Token Expiration Window" 1h/24h/7d buttons (`:760-779`) store `tokenExpiry` state (`:93`) that is never passed anywhere — `api.enroll` takes only a name (`src/api.ts:253`: `enroll: (name) => call("/api/devices/enroll", "POST", { name })`; call site `DevicesView.tsx:223`). The modal also shows a 4-step progress `["Name","Token","Install","Heartbeat"]` (`:668-671`) whose `current` is `hasRealToken ? 2 : 0` — the "Heartbeat" step is never tracked; the user is just told to `"watch Live home for the first heartbeat"` (`:674-677`). In demo mode, enrolment pretends to succeed: `handleEnrollDevice` (`:218-240`) skips the API, sets `tokenProvisioned(true)`, and auto-closes the modal after 800 ms with no token ever issued — while the copy says `"Demo preview only — no real device token is issued."` A user who skims sees a success animation and a closed modal.
- **User impact:** Users may believe they configured architecture/sandbox/expiry when nothing was sent; the fake progress bar implies the flow is tracking install/heartbeat when it is not.
- **Recommendation:** Remove the three dead controls (or wire them to the API); remove the Heartbeat step or poll for the first heartbeat and advance the progress for real. In demo mode, keep the modal open on an explicit "This was a preview — no token was issued" end state instead of auto-closing as if done. Prefer converging on the live `Inventory.Enrollment` modal (`src/views/live/Inventory.tsx:9-57`), which has none of these traps.

#### UX-08 — Four buttons promise actions they do not perform [P1, VERIFIED]
- **Problem:** Live-mode controls whose labels promise a real action, but which fabricate the result in the browser.
- **Evidence:** (1) "Add client" / "Test Handshake & Sign Token" — `src/views/ConnectionsView.tsx:718,1070` → `handleSignToken` (`:518-533`) builds `header.payload.signature` in the browser with `const sig = "MEQCID3k8e8...ed25519";` and displays it as a token; no `POST /api/connections/clients` exists. The fake JWT can be copied out (`handleCopyJwt`, `:536-540`, 2 s "copied" feedback) and pasted into a real client, where it will fail opaquely. (2) "Rotate secret" — `:706` → `handleRotateSecret` (`:458-476`): live branch only re-fetches connections and shows `"Gateway secrets are managed by the control plane… Refreshed active token state."`; demo branch fabricates `"Master Gateway Secret successfully rotated. New ephemeral keys deployed to all active SSE streams."` Nothing is rotated in either branch. (3) "Capture snapshot" / "High-res desktop frame buffer captured (3840×2160 PNG)" — `src/views/LiveDesktopView.tsx:948-957`: sets the notice, only calls `fetchLiveFrame(1.0, 85)`, clears after 2.5 s. No PNG is produced or downloaded. (4) "Verify integrity" — see UX-01. The one honest case is "Simulate key generation" / "Preview only · no key is issued" (`src/views/DevicesView.tsx:846-867`) — the pattern the other four should follow.
- **User impact:** A signed-in admin can believe they created a real credential or rotated a real secret.
- **Recommendation:** Remove or gate (1), (2), (3), (4) until real endpoints exist; if a demo affordance is kept, label it exactly like (5) ("Simulated — no real token is issued").

#### UX-09 — Task follow-through is broken by default in the main Tasks view [P1, VERIFIED]
- **Problem:** After dispatching, the user has no clear confirmation of where the task is or when it finishes — and the default list may not even contain the authoritative record.
- **Evidence:** `src/views/TaskQueueVisionView.tsx:174-178` — `useServerHistory` defaults to `false`, so the list is the store's synced list, not server history. The live server history (with pagination, `api.taskHistory`, `:438-442`) requires the user to tick `"Search full server history (paginated)"` (`:859-872`). Live task detail/events are fetched only for the selected task (`:532-550`). There is no auto-refresh/polling visible in this view; a dispatched task's status change is not pushed to the user, and `handleDispatch` (`:256-285`) only sets `selectedTaskId` and calls `refreshLive()` — no "now tracking task X" state, no link to the task, no toast beyond `jsonError` on failure. The live `TasksPanel` does this better: `"Submission is not completion. Follow progress in Tasks."` (`src/views/live/TaskComposer.tsx:50`) and per-task `<details>` with `TaskResult` + `TaskEvents` (`src/views/live/TasksPanel.tsx:104-115`). Approval-gated tasks dead-end in the queue: if no matching pending approval exists, clicking Approve yields only `"No pending approval record found for task #..."` (`:354-356`) — a notice, no link to the Approvals view.
- **User impact:** The primary task flow ends in ambiguity; an approval-gated task leaves the user with nowhere to go.
- **Recommendation:** Default `useServerHistory` to true when live (or unify the list on server history); after dispatch show a persistent "Task #id — status" affordance linking to the task row, with live status updates; link approval-gated rows to the matching approval in Human Approvals (show approval id/status inline).

#### UX-10 — Most forms are not `<form>`s, and the workflow builder is a hand-rolled dialog [P1, VERIFIED]
- **Problem:** Only 5 `<form>` elements exist in all of `src/` (grep): `src/views/AiApiHubView.tsx:2500` (Copilot chat), `src/views/LoginView.tsx:98`, `src/views/live/AccountsPanel.tsx:29`, `src/views/live/DeviceWorkspace.tsx:45`, `src/views/live/LiveWorkspace.tsx:125`. Only 6 `type="submit"` occurrences. Every other data-entry surface submits via `onClick` — enrolment `onClick={handleEnrollDevice}` (`src/views/DevicesView.tsx:864`), task dispatch `onClick={handleDispatch}` (`src/views/TaskQueueVisionView.tsx:819`), workflow `onClick={() => void submit()}` (`src/views/WorkflowsView.tsx:675`), policy save `onClick={() => void saveDevice()}` (`src/views/SecurityPoliciesView.tsx:420`), AI save `onClick={handleSaveAi}` (`src/views/AiApiHubView.tsx:1318`), MCP create `onClick={() => void handleCreateMcpServer()}` (`src/views/AiApiHubView.tsx:1585`). Keyboard users cannot submit with Enter (except the one documented ⌘/Ctrl+Enter shortcut in the task studio, `TaskQueueVisionView.tsx:579-582`); browser autofill/validation/password-manager behaviours that key off `<form>` do not apply; `required`/`minLength` are unenforceable outside a form. Separately, the workflow builder is a hand-rolled dialog, not `GlassModal`: `src/views/WorkflowsView.tsx:603-606` — `<div role="dialog" aria-modal="true" aria-label="New workflow" …>` with no Escape handler, no focus trap, no focus return, no backdrop-click close (contrast `src/ui.tsx:352-391`). Keyboard/screen-reader users can tab out of it into the inert background; Escape does nothing (the help modal in `src/shell/AppShell.tsx:115` documents "Close modal / menu — Esc", which is false here).
- **User impact:** Keyboard users cannot use Enter to submit most forms; the workflow dialog traps no focus and ignores Escape.
- **Recommendation:** Wrap each in `<form onSubmit={…}>` with `type="submit"` on the primary button; replace the workflow builder div with `GlassModal` (native `<dialog>`, focus trap/Escape/backdrop-close/focus return).

#### UX-11 — The Live Desktop canvas is an unnamed focusable region that silently forwards keystrokes to a remote machine [P1, VERIFIED]
- **Problem:** The stream viewport is focusable but has no name, no role, and no warning that typing goes to a remote computer.
- **Evidence:** `src/views/LiveDesktopView.tsx:1910-1922` — `<div ref={canvasContainerRef} tabIndex={0} onMouseMove… onKeyDown={handleCanvasKeyDown} …>` with **no `role` and no `aria-label`**. The `<video>` inside (`:1924`) has no `aria-label` either; the fallback `<img>` does have `alt="Remote desktop stream frame"` (`:1963-1965`). `onKeyDown`/`onKeyUp` forward keys to the remote host (`handleCanvasKeyDown`, `:1915`); there is a "Focus: Container [tty1]" text indicator (`:1904-1907`), but nothing tells a screen-reader user what the focused element is or that typing will go to a remote machine.
- **User impact:** A keyboard user tabs onto an unnamed focusable region; keystrokes are silently sent to a remote desktop — a surprising and potentially destructive interaction with no accessible warning.
- **Recommendation:** Add `role="application" aria-label="Remote desktop. Keyboard input is sent to the remote computer."` (or `role="region"` + label + a visible hint), and an accessible "release keyboard focus" mechanism. Related: Esc is hijacked for agent-intent veto (`LiveDesktopView.tsx:371-381` — Esc/Space veto a pending agent action via `e.preventDefault()`), so Esc never releases the session; make Esc (outside the veto window) switch to Observer mode or show an explicit "Release control (Esc)" affordance.
